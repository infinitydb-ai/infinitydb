# InfinityDB Changelog

## Unreleased

- feat(local-models): **`pip install "infinitydb-ai[onnx]"` puts a local semantic signal behind an optional extra.** New `infinitydb.local_models` exposes `local_embedder()` (FastEmbed `BAAI/bge-small-en-v1.5`), `local_reranker()` (`Xenova/ms-marco-MiniLM-L-6-v2` cross-encoder) and `local_dense_index(db)`, each CPU-only, key-free and offline after the one-time model download. Nothing imports it automatically: `dependencies = []` is unchanged, and the default path still makes no network call. The module raises an actionable `Install the optional local-model extra: pip install "infinitydb-ai[onnx]"` instead of a bare ImportError. Three tests stub fastembed so the error path and the wrapper contract run on a bare install.
- bench: **the opt-in reranker wins at Mem0's token budget — the first matched-token win, published with its latency cost.** Same 4 conversations, 99 sessions, 584 questions, `k=10`, in one session in which `mem0_nollm` reproduced its 74.40% at 418.7 tokens exactly ([locomo-token-grid-results.json](benchmarks/locomo-token-grid-results.json), per-question logs for both InfinityDB 420-token rows): `recall(..., budget_tokens=420, rerank=local_reranker())` scores **76.80% evidence recall at 406.0 tokens**, 2.40 points ahead of Mem0 on 3% fewer tokens, against **69.07%** for the same call without the model. Paired on the same questions the reranker fixes 81 and breaks 36 (McNemar exact p = 3.9e-5), and a second run reproduced both numbers exactly. The write path is untouched: ingest p50 stays 29.1 ms because there is no index to embed. Recorded beside the win: **1,335 ms p50 search** versus 30 ms lexical and 257 ms Mem0, so this is a quality win, not a speed one; dense fusion with Mem0's own `thenlper/gte-large` scores **70.96%** and loses, so the gain is the cross-encoder's joint query-passage encoding rather than a bigger embedding; and `dense=`+`rerank=` reaches only 77.15% for 1.6 s more search, so the recommended opt-in is the reranker alone. The full 320/420/600/1000/1750 curve is measured for default and dense fusion; the reranker is one budget point because a reranked run costs ~10× a lexical one.
- feat(engine)+bench: **the reranker is now affordable: `rerank_top_k` and INT8 take it from 616 ms to 135 ms p50, and it still beats Mem0 at a matched budget.** The matched-token win shipped as a 1.3 s-per-query feature, which is not a feature most agents can turn on. The engine assembles up to `3*k = 30` chunks and cross-encoded all of them; `recall(rerank_top_k=8)` now cross-encodes only the eight highest lexical candidates and lets the tail fill leftover slots, and `local_reranker(quantize=True)` runs a dynamically quantized INT8 copy of the same MiniLM model (built once, cached, `onnx` added to the `onnx` extra). Gates were set before the runs: search p50 ≤ 300 ms and evidence recall ≥ 75.0%. Same 584 questions, `k=10`, budget 420, one run at a time ([locomo-rerank-latency-results.json](benchmarks/locomo-rerank-latency-results.json), per-question logs for all four rows): rerank-all fp32 **76.80% / 616.1 ms**, rerank-all INT8 76.29% / 453.1 ms, top-8 fp32 76.46% / 176.3 ms, **top-8 INT8 75.60% / 135.5 ms at 411.8 tokens** — both gates pass, and it is 1.20 points ahead of Mem0 `infer=False` (74.40% at 418.7 tokens, 257 ms) on 2% fewer tokens. Paired per question: top-8 INT8 vs the lexical default fixes 66 and breaks 28 (McNemar p = 1.1e-4); vs reranking everything it is 10 fixed vs 17 broken (p = 0.25), so the 4.5× cut is not a measurable recall loss on this harness. Recorded beside it: 135 ms is still 4.5× the 30 ms lexical path, quantization is an extra cached artifact, and the earlier published 1,335 ms figure was measured under three-way CPU contention — re-measured sequentially the full pass is 616 ms, which is the number now published.
- docs: **the MCP server is now the first quickstart in the README**, above the demo: `claude mcp add infinitydb -- uvx --from infinitydb-ai infinitydb-mcp`, with the adoption cost (0 extra packages, ~2 ms p50 recall, 19.8 MB RSS) quoted from the measured friction page.

## 1.4.2 — 2026-11-18

Three things in this release point in different directions on purpose: a new opt-in
API, the measurement that says not to use it, and a command that reports both.

```bash
pip install -U infinitydb-ai
infinitydb-evidence        # 5 checks, PASS/FAIL, then this project's known limits
```

- bench: **a fully local, zero-key comparison harness, and the numbers it produced for InfinityDB alone.** `benchmarks/locomo_local_compare.py` runs LoCoMo with no API key, no hosted service and, for InfinityDB, no model at all; the Mem0 and Cognee adapters (Ollama) and a flat dense-vector baseline are imported only when selected, and one whose dependency is missing is recorded under `skipped_engines` instead of aborting the run. It reads the `locomo10.json` the arena already vendors, so a run needs no network. Measured, 10 conversations, `k=10`, 1,540 answerable questions (category 5 excluded): **evidence recall@10 87.1%**, retrieval p50 21.8 ms / p99 54.9 ms, ingestion p50 29.3 ms per ~20-turn session, 1,643 retrieved tokens against 18,468 for the full conversation (91.1% fewer), with `tiktoken/cl100k_base` recorded as the counter. Two runs reproduced every accuracy column exactly. Stated beside it: the gold-answer containment (35.97%) and token-overlap F1 (5.61%) columns are string tests that punish long context and are not reader accuracy, and no competitor row was measured here because this host has no Ollama or model weights — those numbers remain the arena's pinned-virtualenv ones. `tencentdb_local` is a flat dense-vector baseline, not the TencentDB product, and the report names its backend.
- feat(engine)+bench: **turn-level packing exists, is opt-in, and lost.** The follow-up to the equal-token negative was to give the packer more slots by splitting merged chunks into individual turns and scoring them against the query, so the same budget buys ten small chances instead of 2.8 large chunks. `recall(..., pack_fragments=True)` does exactly that with no model on either path, and `recall(..., token_counter=...)` lets the caller count the budget in its own units — the harness now passes `tiktoken`, so `--budget-tokens 419` is 419 real tokens instead of the old word budget that drifted to 521. Measured, same four conversations and 584 questions, `k=10` ([logs](benchmarks/locomo-fragment-pack-results.json)): at 409.7 tokens splitting scores **67.70% evidence recall** against whole chunks' 69.07% at 408.9 tokens and Mem0 `infer=False`'s **74.40%** at 418.7 — the ten-slot hypothesis is refuted. Whole windows win because the evidence turn is often a *neighbour* in the winning window rather than its best-scoring turn, and the turn selection is lexical where Mem0's is `gte-large` cosine. The mode stays opt-in because a measured-worse mode must not change existing `budget_tokens` behaviour. One number kept deliberately: splitting lifts the token-overlap F1 proxy from 4.31% to 14.05% (Mem0: 14.44%) while evidence recall falls, which is the clearest evidence yet that F1 at matched tokens measures context length, not answering. Limitation recorded in the same section: with `n` slots, budgets above `n` turns are not spent (600 → 414.6 tokens).

- bench: **the equal-token control came back negative, and it is now the headline.** The previous bullet left one hole open: InfinityDB's +13.57-point evidence-recall lead over Mem0 `infer=False` was measured at 1,748 retrieved tokens against Mem0's 419, so the lead could have been context rather than retrieval. `--budget-tokens N` now re-runs the same engine through `recall(budget_tokens=N)` and the harness reports **returned items** per query beside tokens, because a budget buys recall by returning fewer, larger snippets. Same four conversations, 584 questions, `k=10` ([per-question logs](benchmarks/locomo-equal-token-results.json)): at 433 tokens (budget 350, 3.3% above Mem0's 419) InfinityDB scores **70.45% evidence recall against Mem0's 74.40%** — 3.95 points behind — and needs **521 tokens, 24% more**, to draw level (74.23%). The 87.97% row therefore stands only at 4.2x the context: the recall lead is a context purchase, not a free win, and the budget cannot close the gap at Mem0's footprint. Also recorded: budget enforcement trades recall for cost instead of compressing (containment falls with it, so shorter context is not more precise), no budget reaches Mem0's answer-level F1, and the engine's `budget_tokens` is enforced as a *word* budget inside `recall`, so measured tiktoken tokens run ~1.24x the setting — the reported token column is the measurement, never the setting.

- bench: **the zero-LLM write-path comparison, measured and published as a trade.** The harness gained a `mem0_nollm` row: Mem0 OSS 2.2.1 in its documented `infer=False` mode — every turn stored as written, embedded with FastEmbed `thenlper/gte-large` on CPU, retrieved from local Qdrant — which is the only Mem0 configuration comparable to a write path with no LLM. Same four conversations, 99 sessions, 584 questions, `k=10`: ingestion p50 **32.9 ms vs 1,494 ms** per session, retrieval p50 15.7 vs 147.6 ms, evidence recall@10 **87.97% vs 74.40%**, but retrieved context **1,748 vs 419 tokens** and answer-level F1 5.48% vs 14.44%. Recorded beside the win: ten InfinityDB slots are ten merged chunks and ten Mem0 slots are ten single turns, and the equal-token control that settles whether the lead is context or retrieval was run separately and **lost** (see the bullet above); the LLM-extraction Mem0 that the "no LLM in the write path" claim is actually about remains unmeasured, because this host has no Ollama.
- feat(evidence): **`infinitydb-evidence`, a self-audit command for people who don't believe the README.** Runs the demo, measures ingest/recall latency on the current machine, round-trips an audit bundle including a tampered record that must be rejected, imports a fixture twice to prove idempotency, and performs a real MCP `initialize`/`tools/list` handshake against a freshly spawned server. Exits non-zero if any check fails, so it can gate CI or a procurement review. It prints the project's known limits **after** the passes, from one list in code: the multi-hop result where plain retrieval beats bridges, the open-domain loss to mem0, no independent reproduction, no encryption at rest, `user_id` as a string not a security boundary, and measurement only to 5,000 facts. `--with-arena` recomputes the published table; `--json` for machine consumption. Companion [docs/OBJECTIONS.md](docs/OBJECTIONS.md) separates the objections with an answer from the five without one, and lists the tests that would settle each open claim.
- perf(engine): **memoise `_stem` and stop paying two round trips for BM25 corpus stats.** A profile of `recall` showed 42,100 calls to `_stem` for 20 queries: every candidate fact re-stemmed the same vocabulary from scratch. The function is pure, so it is now `lru_cache`d. `total_atoms` and `_average_fact_tokens` were two separate `SELECT`s per recall; `_corpus_stats()` returns both in one statement. Measured on the 2,000-fact latency corpus: median read 6.05 → ~5.5 ms, P95 8.5 → 6.1-7.4 ms, P99 write 4.42 → 3.53-3.77 ms. Ranking is untouched — the full arena reproduces evRec 0.8480 / inCtx 0.5935 / 1426 words exactly, and `arena.py verify` passes.
- bench: **latency targets are measured instead of asserted**, via `benchmarks/latency_targets.py` (P99 write, and P50/P95/P99 read for both the plain and multi-hop configurations, plus a matched-budget read). Results: P99 write **met** (3.53-3.77 ms vs 5 ms); P50 and P95 read **met**; P99 read **not met and not stable** — three identical runs produced 8.20, 10.76 and 12.77 ms, with no overlap in the slow queries between passes, so the tail is host scheduling noise rather than a code path. On LoCoMo the same read path is p50 13.11 ms.
- docs: **`docs/SPEC_CONFORMANCE.md`** maps every clause of the project brief onto the code that exists, marking it present / partial / absent. It records, without softening: there is no Rust core (only ~40 lines of score-fusion primitives in `alpha-v2/rust`), no ONNX models (`dependencies = []`), no background "dreaming" workers, no `org_id`/`agent_id`, no ANN index in the stable core (HNSW is `alpha-v2`-only), and no gRPC. It also records the LongMemEval number that exists: recall@5 0.9333 on 180 of 500 questions at 534 words median context.

- bench: **the cost frontier is measured as a curve, and the new chunking dominates it.** Phase 2k published one unflattering point (old chunking at 20 slots: 0.8795 at 1,852 tokens beat anything the new defaults produced), which was a comparison of single points. Measuring the whole curve: new chunking `n=12` scores **0.8841 at 1,659 tokens** — above the old chunking's best, with 8 fewer slots and 193 fewer tokens — and at every measured level from 1,170 tokens up the new chunking is at or above the old, with a higher recall-per-token at every point but the last (0.726 vs 0.475 at the extremes). Two caveats stated in the same section: the 0.8841 row is recall over 12 memories and must not be quoted as `@10` (that remains 0.8729), and the mechanism is unchanged — the frontier moved, not the retrieval idea. No engine change: the practical advice is that callers who wanted 20-memory quality should ask for 12.

- feat(engine): **deeper assembly and 12-turn chunks lift evidence recall to 0.8480 — with the cost-matched result published beside it.** `_ASSEMBLY_DEPTH` 240 → 1000 and `_MAX_CHUNK_TURNS` 8 → 12: LoCoMo @10 over 1,986 questions gives evidence_recall@10 **0.8480**, answer_in_context 0.5935, **multi-hop 0.6260**, single-hop 0.9516, temporal 0.8622, open-domain 0.5186, adversarial 0.9585 — every category up. CPU cost 1.01× (16.8 ms vs 16.5 ms at 2,000 facts; 67.9 vs 67.4 at 10,000). Context cost is the real price and is stated with the number: median 1,248 → 1,426 tokens, and 711 at the pre-2i baseline. **The honest control is in Phase 2k:** the same engine with the old chunking returning 16 memories scores 0.8676 at 1,497 tokens, so at matched context this is +0.005, not +0.068 — the advantage that holds is at a fixed ten slots. Gate 2a (multi-hop ≥ 0.55 at `top_k=10`) is met on its published definition (0.6260) and the doc records that a slot-count gate can be satisfied by packing more text into a slot, which is why token cost must accompany the metric from here on.

- feat(engine): **multi-hop clears Gate 2a — 0.5952 against 0.55 — by widening returned chunks from 4 turns to 8.** Assembly capped a chunk at 4 turns, the smallest span that can express one three-turn neighbour window; multi-hop answers routinely need the turn after that. Raising the cap (`max_chunk_turns`, default 8) gives, on LoCoMo @10 over 1,986 questions: evidence_recall@10 **0.8324** (from 0.780 two releases of work ago, 0.8069 in 2i), answer_in_context 0.5805, **multi-hop 0.4939 → 0.5952**, single-hop 0.9421, temporal 0.8549, open-domain 0.4639, adversarial 0.9484 — every category up. Paid for in context, stated with the number: median returned context 963 → 1248 tokens (+30%), p50 latency flat at 12.6 ms. Reviewed against the equal-budget rule, because a wider chunk buys context: span-8 at `k=10` scores 0.6206 at 1,419 tokens, beating plain retrieval capped at ~1,420 tokens (0.6018) — so the win holds at equal tokens, unlike the bridge arm in 2f. Plain retrieval at 1,871 tokens still reaches 0.6491, which is the honest limit: this moves the frontier, it does not make context free.

- feat(engine): **multi-hop +0.042, overall evidence recall +0.027 — from a truncation bug, not a new mechanism.** Chunk assembly merges adjacent turns, and then returns `n` chunks, but it only traversed the top `3*n` ranked items. The turn that completes a multi-hop question usually sits below position 30, so an asking caller with `k=10` could never receive it; the same shallow traversal also returned fewer than `n` chunks, which triggered a second full `_recall_atoms` scoring pass to fill the slots. `recall(..., assembly_depth=...)` decouples traversal from `n`, and the default now traverses 240 items. Measured on LoCoMo @10, 1,986 questions: evidence_recall@10 **0.780 → 0.8069**, answer_in_context 0.545 → 0.5584, multi-hop **0.4939 → 0.5359**, single-hop 0.9128 → 0.9326, temporal +0.030, open-domain +0.045, adversarial +0.018 — every category up, nothing down. Cost stated where it is paid: median context 711 → 963 tokens (+35%), p50 latency 10.7 → 12.6 ms. Arena rows regenerated and `arena.py verify` reproduces the new headline from the committed rows; older tables in DILIGENCE/LEADERBOARD/TEARDOWN are left as historical records of the previous default.

- bench: **Phase 2h: query expansion tested at equal slots — negative, and it found two silent no-ops.** Pseudo-relevance feedback (re-querying with names mined from the top hits) was the cheapest candidate for Gate 2b. It **raises @1 to 0.1803**, the best precision@1 in the programme, and **lowers @10 to 0.4513** — the added terms promote the bridge sentence and evict other needed evidence, so at equal slots it is a net −0.0426. Two bugs were caught by measurement rather than by reading: `recall(entities=…)` is an AND filter, not a boost (passing discovered names produced an *exactly* identical 0.4939 — a no-op signature), and the probe's `if not bridges: continue` guard ran before the new mode, short-circuiting every question to the baseline. Fixing both produced real numbers. Ablating the engine's own PRF also shows the shipped default is load-bearing: `expansion=0.0` scores 0.4755 and `0.3` scores 0.4795 against the default 0.15's 0.4939. Probe gains `--mode expand`, `--seed-k`, `--expand-terms`, `--engine-expansion`; four result JSONs committed.

- bench: **Phase 2g: the equal-budget control closes the bridge programme.** Phase 2f's +0.0228 came from appending witnesses, which used 18 context slots; nothing held slots constant. With the same 18 items on the same 249 questions, **plain retrieval scores 0.5714 against the bridges arm's 0.5164 — a 5.5-point loss for bridges**. The gain was context, not graph evidence. `recall_with_bridges` stays as an opt-in inspection tool and is now documented as negative against an equal-slot baseline rather than as an improvement. Gate 2 is restated as two conditions: 2a (multi-hop ≥ 0.55 at top_k=10, unchanged) and **2b (any mechanism must beat plain retrieval at equal slots)** — currently unmet by 0.055. Probe gains `--compare-budget`, which runs the control in the same pass so the comparison cannot be forgotten again.
- feat(bridge): **`recall_with_bridges()` exposes the additive mechanism, opt-in.** Returns the normal recall result with the quoted witnesses appended and labelled `source: "bridge"` instead of spending retrieval slots on them, plus the chosen edges and which selector ran. Defaults to `SubjectBridge` with `max_bridges=8` — the configuration that measured 0.5167 — and accepts any selector, including `NullBridge` for a no-op. Deliberately a library call rather than a `recall()` parameter: the 0.55 gate is not cleared, so no default path changes. Five tests hold the shape that mattered — witnesses never displace a retrieved turn, the selector is respected, duplicate sentences collapse.
- bench: **Phase 2f: bridge evidence must be additive, and that changes the result.** Every earlier arm spent a recall slot per quoted witness, so at 10-slot context a witness replaced a turn the retriever had already found. Two ranking signals were tested first and both lost (question overlap −0.0386, novelty −0.0487 at 89% coverage), which looked like "lexical signals cannot rank witnesses". Appending witnesses instead of displacing them (`--extra-budget`) shows the confound: the same 89%-coverage selector goes from **−0.0254 to +0.0228**, monotonic from cap 2 (+0.0098) to cap 8 (**0.5167**). Best multi-hop result in the programme and still short of the 0.55 gate; the gain costs ~8 extra sentences in context, and single-hop impact is unmeasured. Recorded in `docs/SELF_IMPROVEMENT.md` with the ranking signals explicitly marked as not-yet-fairly-tested.
- feat(migrate): **`infinitydb-migrate` imports an existing memory layer from a file, in one command.** Reads mem0's `get_all()` JSON, generic JSON, JSONL transcripts and plain text with no competitor SDK installed and no network call. `created_at`/`timestamp`/epoch-ms become event time so `as_of` and decay stay correct, and records without a timestamp are counted and reported rather than silently stamped with import time. Re-runs are idempotent (checked against `l0_logs` before writing), `--dry-run` reports without writing, `auto_supersede=False` so an import cannot delete a newer fact, and the command verifies itself by recalling the first imported memory. Ten tests cover the mem0 shape, role handling, millisecond timestamps, malformed JSONL lines, dedupe, idempotency, dry-run and both CLI exit paths. `docs/MIGRATE.md` states what does not come across — embeddings, another product's graph edges, supersession history, scores — and says plainly that removing switching effort is not a reason to switch.
- feat(readme): **the repo now shows itself working, as an animated SVG generated from a real run.** `scripts/make_demo_svg.py` executes `python -m infinitydb.demo`, captures stdout and renders it as a typewriter terminal animation (`assets/demo.svg`, 4.9 KB, no GIF host, no binary, scales on retina). Every non-timing line must still match the demo's live output or `tests/test_demo_svg.py` fails, so the image cannot drift into advertising something the code no longer prints. The SVG carries the full transcript in `<title>`/`<desc>` for screen readers and indexing, contains no script or remote reference, and honours `prefers-reduced-motion` by showing the whole transcript instead of a blank frame. Also fixed the demo printing "1 memories".
- feat(audit): **`infinitydb-audit` CLI — export, verify and attest from the shell.** `export --db … --user … [--out] [--no-text]` writes a bundle and prints the digest to anchor; `verify <bundle> [--anchor] [--json]` re-derives everything offline and names the failing records; `receipt --yes` erases and writes deletion evidence; `verify-receipt` checks it. Exit codes are the contract (0 verified, 1 failed, 2 bad input) so a script can branch without parsing output, and `verify` needs only the bundle file — not the database, not the API. Six subprocess tests cover the round trip, a tampered bundle, an anchor mismatch, digest-only export, the `--yes` guard and unreadable input.
- feat(audit): **portable, tamper-evident audit bundles and erasure receipts.** `audit.export_bundle(db, user_id)` returns JSON holding every fact with its L6 proof hash, the digest of the source text it came from, and a hash chain over the whole record; `audit.verify_bundle(bundle)` re-derives all of it offline from the bundle alone, and accepts an `anchor` digest so a later bundle that no longer matches proves the record was edited or deleted. Editing a fact, dropping one, reordering two, or withholding text all fail verification with a named reason. `erase_with_receipt(db, user_id, confirm=True)` erases a tenant and returns a receipt carrying the pre-erasure digest and per-layer counts. Exposed over MCP as `audit_export`, `audit_verify` and `erase_with_receipt` (13 tools now). Measured: 1,000 facts export in 24 ms and verify in 17 ms (522 KB); 5,000 in 126/91 ms — both linear, so a third party can check a real tenant without the database. The guarantee is stated with its limit in `docs/AUDIT.md`: an *anchored* bundle is edit- and deletion-evident, an unanchored one is only self-consistent, and history rewritten before the first export is undetectable. Not signed, no PKI, and not a substitute for encryption at rest.
- feat(demo): **`pip install infinitydb-ai && python -m infinitydb.demo` now shows memory working with no clone and no config.** Three fixed turns are ingested in memory, facts are extracted, and three questions are answered — with timings and layer counts printed. Registered as the `infinitydb-demo` console script. The README leads with that command and its real output, then with the MCP one-liner (`claude mcp add infinitydb -- uvx --from infinitydb-ai infinitydb-mcp`), because the previous install path ended at a prompt: the quickstart lived in `examples/`, which is not shipped in the wheel. A ready-to-copy `.mcp.json` now sits at the repository root, and `docs/MCP_SERVER.md` documents the `uvx` path — verified against the published package. Tests run the demo as a module with proxies pointed at a dead port and assert the recalled facts.
- fix(mcp): **the default store no longer depends on the host's working directory.** It is now the absolute `~/.infinitydb/memory.db`, the same file `infinitydb.capture` writes, so auto-captured turns are visible over MCP instead of landing in a second database. `INFINITYDB_PATH` still overrides it and `:memory:` still works for throwaway use; a parent directory is created on open. `docs/MCP_SERVER.md` gains a scope table (global / per project / per host / throwaway), a rule that host configs use absolute paths, and migration notes: servers started before this change may have written `infinity_mcp.db` into the host's cwd — that file is untouched and simply no longer picked up. Two tests cover it: a spawned server with no `INFINITYDB_PATH` writes to `$HOME/.infinitydb/memory.db`, and the env override still wins.
- feat(mcp): **the MCP server's adoption cost is now measured, and its version matches the package.** `scripts/measure_mcp_friction.py` spawns the real server and records what a host pays: **0 third-party dependencies**, 60.6 KB wheel, **65–82 ms** cold start to a valid `initialize` reply, `tools/list` in 0.1–0.2 ms for 10 tools, `add_memory` p50 1.3–1.8 ms, `recall_memory` p50 1.9–2.5 ms, 19.8 MB peak RSS, 7 lines of JSON to configure. `tests/test_mcp_protocol.py` verifies the transport end to end over real stdio (handshake, `tools/list`, a write, a recall, unknown-method error) — previously only `handle_call_tool` was tested. `SERVER_VERSION` was stale at `1.3.0` while the package was `1.4.1`; it is pinned and a test now fails if the two drift. The doc's "sub-millisecond lookups" claim was replaced with the measured round trip.
- bench: **Phase 2e: witnesses must be appended, never promoted — and recall@10 cannot tell.** `--position top` puts the quoted witnesses first instead of after the retrieved head. Because `score.evidence_hit` joins the context into one blob, @10 is identical by construction (0.5000 either way); the prefix shows the damage: **@1 0.1750 → 0.1517, @3 0.3181 → 0.2881** overall, and on the 49 questions that fire **@1 0.1488 → 0.0153, @3 0.2747 → 0.1027**. The witnessing turn is an intermediate hop's sentence, not the answering one. This also means the +0.0061 in 2d is an inclusion effect, not a ranking effect, and any ranking claim has to be made at @1/@3.
- bench: **Phase 2d: widening the aspect vocabulary is the best multi-hop arm so far.** `BroadPredicateBridge` keeps the strict gate's structure but adds words like `research`, `career`, `activities`, `hobby` and `thesis`, so LoCoMo's "What did Caroline research?" phrasing can fire. Coverage rises from 22 to 49 of 281 questions (7.8% → 17.4%) and the overall result improves to **0.5000 (+0.0061)**, the highest measured. The per-question effect roughly halves (+0.0568 → +0.0347), so precision held in sign but not in size: the narrow gate had been selecting unusually easy questions. Extrapolating +0.0347 to full coverage gives ≈0.529, still short of the 0.55 gate — the next step must raise the effect per question, not just coverage.
- bench: **Phase 2c: raising bridge coverage by naming the person costs more than it gains.** `SubjectBridge` accepts any edge whose subject the question names, plus inbound edges as second-hop witnesses. Coverage rose from 22 to 249 of 281 multi-hop questions (7.8% → 89%) and recall fell: **0.4685 (−0.0254)** at cap 2 and 0.4575 (−0.0364) at cap 3, worse than the baseline even on the fired subset (−0.0287). A test caught that the first version made second-hop witnesses unreachable (an inbound edge's object is the shared node, not the named person); fixing it added 12 questions of coverage without changing the conclusion. Naming a person does not identify which of their sentences answers the question, so the selector has to bind question *aspect* to edge predicate rather than link persons. Both cheap signals now have measured bounds.
- bench: **Phase 2b: quoting the witnessing turn is the first arm to beat the multi-hop baseline.** The probe can now append the turn that asserted each edge instead of scoping retrieval by the bridge object. Quoting every witness costs 0.0415 overall rather than the 0.2471 that scoping costs, and combining it with the strict predicate gate lands at **0.4984 vs 0.4939 (+0.0045)**, with **+0.0568 on the 22 questions where the gate fires** (0.4583 → 0.5152). Capping at two witnesses beats one. Coverage, not accuracy, is now the constraint: the gate fires on 7.8% of multi-hop questions, and +0.057 at full coverage would be ≈0.55, the Phase 2 gate. Recorded with the wide-interval caveat in `docs/SELF_IMPROVEMENT.md`.
- feat(core): **bridge-selector interface for multi-hop work** (`infinitydb/bridge.py`): `Bridge`, `NullBridge` (default, vetoes everything), `AllBridge` (upper-bound arm), `PredicateBridge` (deterministic aspect-matched gate). Nothing calls a selector in the default path; it exists so the multi-hop hypothesis can be measured instead of asserted.
- bench: **Phase 2 scaffold measured: using bridge objects as an entity scope loses recall, even with no filtering at all.** `benchmarks/arena/bridge_probe.py` reproduces the published multi-hop baseline exactly (0.4939 on n=281) with the null selector, which is what makes its comparisons worth reading. Accepting every edge scores **0.2468 (−0.2471)**; the strict predicate gate fires on 1 of 31 questions in conv-26 and scores 0.4778 (−0.0161) over the full set. The mechanism, not only the gate, is therefore suspect: a learned selector would have to be near-oracle to approach the baseline from a design that halves recall when noisy. Recorded in `docs/SELF_IMPROVEMENT.md` with the next hypothesis (quote the witnessing turn instead of scoping by object).
- bench: **Phase 1c: deployable labels keep about 40% of the ranker gain.** Training the same perceptron on labels a deployment can actually produce — top-3 agreement between the existing ranking and an independent overlap/recency ranking, abstaining on everything else, reading neither the answer nor the evidence ids — yields held-out `recall@3` +0.0052, +0.0069 and +0.0075 across the three folds, against +0.0138 to +0.0188 for gold labels, and exactly 0 at `recall@1`. The weights show the reason (`rank=+6.04` versus `+0.68` with gold labels): the agreement label is partly a function of the base ranking, so the model learns to preserve the order. Label quality is the binding constraint, and re-ranking still cannot move `recall@10`.
- bench: **Phase 1b: a pairwise ranker gains a little at recall@3 and nothing at recall@10.** `benchmarks/arena/pairwise_probe.py` trains a perceptron over eight interpretable features on candidate lists, with the same splits and label schemes as Phase 1 and three folds. Held-out `recall@3` improves in all six configurations (+0.0050 to +0.0188) and `recall@1` in five of six (−0.0025 in one), while `recall@10` is unchanged everywhere because re-ranking cannot add candidates. The corrected gate is **not** cleared: one configuration loses 0.0025 at @1, and the labels still require gold data, so the measured gain is an upper bound rather than a deployable result. Recorded as ~1.4–1.9 points of re-ranking headroom; nothing ships in the engine.
- bench: **Phase 1 of the self-improvement plan failed, and is recorded as a failure.** `benchmarks/arena/feedback_probe.py` fits the feedback prior on half the data and evaluates on the other half, with labels simulated two ways (oracle evidence match, gold-answer containment) and hyperparameters chosen on the fit half only. Held-out `recall@1` fell by 0.0104 (conversation split) and 0.0326 (within-conversation split) with oracle labels; answer labels were flat (+0.0013 at @3 within-split). `recall@10` was identical in every configuration, because re-ranking a fixed candidate list cannot change a set metric — which also showed the gate written in `docs/SELF_IMPROVEMENT.md` was measuring the wrong thing. The prior overfits conversation-specific vocabulary: it improves the fit half every time and degrades the held-out half. `learned_boost` therefore stays opt-in and out of every published number, and the pointwise-prior approach is ruled out for default use.
- feat(core): **feedback substrate for retrieval that learns from outcomes.** `record_feedback(query, atom_id, relevant=...)` stores a caller's judgement append-only; `learned_term_weights()` and `learned_atom_weights()` turn those labels into an inspectable prior, and `recall(..., learned_boost=1.0)` applies it. Opt-in by design: the default is `learned_boost=0`, the prior is capped at +3.0 on the term score, and it cannot retrieve a memory that shares no content term with the query. `clear_feedback()` drops the signal without touching memory. **No retrieval-quality number is claimed** — there is no real feedback corpus yet, and the LoCoMo baseline is unchanged at 0.8101 (`dense=off n=1977`); the phased plan and the gate each phase must clear are in [`docs/SELF_IMPROVEMENT.md`](docs/SELF_IMPROVEMENT.md).
- fix(extract): **third-person facts never reached the single-valued categories.** "User relocated to Berlin last spring" was classified `general` while "based in Munich now" was `location`, so two statements about one person never conflicted and `contradictions()` stayed empty. Location, employer and role patterns now accept a `user` subject (`user moved/relocated/settled to`, `user lives/resides in`, `user is living in`, `user works at`, `user's role is`). The subject is required and limited to `user` on purpose: bare "moved to" would swallow "the team moved to a new office" and supersede a real home, which is why the negative case is a test. `based in` / `located in` were left to the existing subject-less rule so one sentence yields one atom rather than two. LoCoMo is unchanged at 0.8101 (`dense=off n=1977`) because its transcripts are first-person.
- fix(core): **a natural question returned nothing.** `search("work")` and `search("where does the user work?")` returned `[]` against a stored "works at the hospital in Leeds", on both 1.4.0 and 1.4.1. The atom index (`l1_atoms_fts`) is tokenised with `unicode61` and no stemmer, while the turn-window index is porter-stemmed, so the query term was matched as an exact token. FTS now receives stem variants plus a prefix atom (`"work"*`, only for terms of four characters or more), and the BM25 term counter compares stemmed tokens, so `work`/`works`/`working`/`worked` and `deploy`/`deployed`/`deploying` all reach the same fact. Absent words still return nothing — the expansion is a match aid, not a fuzzy search.
- Measured effect: the LoCoMo baseline is **unchanged at 0.8101 overall** (`dense=off n=1977`, `./scripts/verify.sh`), because the arena scores the porter-stemmed turn-window path. This fix targets the atom path used by `AgentMemory` and by prose stores that have no turn windows, so it changes what callers see, not the benchmark table.

## 1.4.0 — 2026-11-11
- feat(core): turn-window recall. Each dialogue turn is stored with its immediate neighbours (`l1_turn_windows`, porter-stemmed FTS5, windows never cross a session) and scored on that window, then adjacent hits are merged into contiguous chunks. On LoCoMo this lifts evidence recall@10 from 0.498 to 0.76 without an LLM. `recall(..., turn_windows=False)` restores atom-only scoring for ablation.
- feat(core): `recall(..., expansion=0.15)` adds light pseudo-relevance feedback: strong terms from the best three chunks are folded back into the query, so paraphrases ("job" for "work") still match. On LoCoMo this lifts evidence recall@10 0.7632→0.7781 and answer-in-context 0.5253→0.5454 (0.1 and 0.3 are worse; `expansion=0` restores the old behaviour).
- feat(core): `recall(..., rerank=fn)` accepts an optional cross-encoder plug-in over the merged chunks. Measured with `ms-marco-MiniLM-L-6`: +0.7% relative recall for 13× the latency, so it ships as an option and is not the default.
- feat(core): `recall(..., budget_tokens=N)` packs the highest-ranked memories into an explicit word budget and always returns at least one, so callers can hold prompt cost constant. At mem0's context size InfinityDB leads its evidence recall and improves answer-in-context by 24%.
- perf(core): stemmed tokens for each turn window are cached between writes, cutting recall p50 from 24.9 ms to 9.6 ms on LoCoMo; the cache is invalidated by `add()` and `delete_user()`.
- feat(core): `stats()` reports `l1_turn_windows`; `delete_user()` erases window rows with the rest of a tenant's data.
- feat(core): **scoped recall**. `recall(..., session_id=..., entities=[...])` restricts the candidate set, and document frequencies / average length are computed *inside* the scope. Measured with `benchmarks/arena/scoped_probe.py` on a store holding all ten LoCoMo conversations: unscoped 0.7331 evidence recall@10, scoped 0.7799 — identical to ten separate databases (0.7799), at 40 ms p50. Without in-scope corpus statistics the same filter recovers only 68% of the loss.
- feat(core): `add(..., extractor=fn)` accepts a caller-supplied extraction callable (any LLM, tagger or batch job) and stores its facts as L1 atoms with L6 provenance, indexed under a `::facts` session so they are never merged into a dialogue chunk. Input is validated, and an extractor failure raises instead of silently storing nothing. Default stays fully deterministic and offline.
- fix(core): a base-verb query could score zero against a past-tense memory ("move" vs "moved") because the stored side was stemmed to "mov"; the candidate was then dropped. Trying the e-final variant fixes it. On LoCoMo: evidence recall@10 0.7781 → 0.7795.
- feat(mcp): the MCP server grows from 5 to 8 tools — `recall_memory` now takes `session_id`, `entities`, `as_of`, `top_k` and `budget_tokens`; new `correct_fact`, `forget` (confirmation required) and `stats`; replies render dated memories for citation.
- feat(capture): `python -m infinitydb.capture --transcript <jsonl>` push-ingests an agent transcript (Claude Code, Cursor) incrementally from a byte-offset state file, so a `Stop` hook can run after every turn without duplicating memories. Partial trailing lines are left for the next run.
- bench: `scoped_probe.py` measures cross-conversation contamination (isolated vs pooled vs scoped) with the same scorer as the arena.
- bench: `longmemeval_probe.py` runs LongMemEval `longmemeval_s` in retrieval-only mode, the dataset MemPalace publishes against: session-level R@5 0.9333 over a stratified 180-question sample (30 per type), ingest 2.0 s/question, recall p50 15.2 ms. Reported as a subsample, not as a win over their full-set 96.6%.
- feat(core): **optional relative-date normalisation** — `add(..., normalise_dates=True)` resolves "last year" / "three days ago" against the event timestamp before extraction, keeping the raw L0 log verbatim. Measured on LoCoMo it costs 0.0024 evidence recall (0.7771 vs 0.7795), so it is off by default; it exists because an Ollama reader answered "Last year." where the gold answer was "2022".
- feat(bench): `score.py --limit N` samples the first N questions per conversation so a CPU-only local reader can score a slice, and `.arena/reader_compare.py` prints generated answers next to gold. Measured with `llama3.2:3b` over Ollama on conv-26: the full QA path runs offline at ~8-12 s per answer; the 10-question sample is committed with its n, not presented as a ranking.
- feat(core): **dense fusion** — `index_dense(embedder, model=...)` stores normalised turn-window vectors, and `recall(..., dense=(embedder, model, weight))` fuses the dense ranking with the lexical one by reciprocal rank fusion. Measured with a local MiniLM (no LLM anywhere): evidence recall@10 **0.7867** vs 0.7795, answer-in-context 0.5487 vs 0.5454, and **652 vs 711 context tokens** at 29 ms p50 (vs 10.7 ms). Weight 1.0 regressed to 0.7768, so 0.3 ships; off by default, because the core still ships no model. The early exit for queries with no lexical match is skipped when dense is on, which is what lets a paraphrase-only question be answered at all.
- feat(core): **typed relation edges**, written at ingest from first-person predicates (`works_at`, `lives_in`, `studied_at`, `likes`, `dislikes`) into `l1_entity_edges`, each pointing at the atom that asserted it. `relations(entity, hops=2)` walks them outbound and inbound, so a shared workplace or place links two people. `rebuild_edges()` backfills databases written before the table existed.
- feat(core): **deterministic contradiction detection.** Same subject + predicate + a different object (or opposite polarity of the same object) supersedes the older fact *and* records the resolution in `l1_atom_relations`; `contradictions()` lists what was replaced, by what and when. History stays readable through `as_of`, and recall no longer returns a superseded dialogue turn (it was only excluded from the atom path before). `auto_supersede=False` keeps it off for multi-party transcripts.
- feat(core): `persona_summary()` returns the resolved persona as one paragraph, for prompts that need "who is this user" without replaying turns. Summarises resolved state only; no retrieval claim attached.
- feat(extract): new `infinitydb.extraction` module with `openai_extractor()`, `ollama_extractor()` and `chat_extractor()` for any OpenAI-compatible endpoint, plus `parse_facts()`. Built on `urllib`, so the core keeps zero dependencies, and an unparsable model reply raises instead of silently storing nothing.
