# Vendor-neutral memory benchmark

The harness can run multiple real adapters over the same deterministic text corpus and query set. It includes InfinityDB's exact-vector baseline plus optional integrations for Mem0 OSS, Zep Cloud v4, and Letta archival memory.

## Install

From `alpha-v2/`:

```bash
pip install -e ".[benchmark-competitors]"
```

Mem0 OSS also downloads/configures its local embedding and Qdrant dependencies on first use. Letta requires an existing agent per tenant. Zep requires a Cloud API key and creates one Zep user per benchmark tenant.

## Configure services

```bash
# Mem0 OSS local persistence
export MEM0_DATA_DIR=.benchmark-data/mem0
export MEM0_EMBEDDING_MODEL=sentence-transformers/all-MiniLM-L6-v2

# Zep Cloud v4
export ZEP_API_KEY=...

# Letta: create one agent for each tenant before running.
export LETTA_API_KEY=...
export LETTA_ENVIRONMENT=cloud
export LETTA_AGENT_IDS_JSON='{"tenant-0":"agent-uuid-0","tenant-1":"agent-uuid-1"}'
```

Letta requires a complete tenant-to-agent mapping for every tenant generated by
`--tenants`. Do not point multiple tenants at the same agent. The benchmark
does not create agents because agent creation requires model/provider
configuration and may incur provider costs.

## Run a head-to-head comparison

```bash
python -m benchmarks.vendor_neutral.runner \
  --adapter benchmarks.vendor_neutral.infinitydb_alpha:build \
  --adapter benchmarks.vendor_neutral.adapters.mem0_local:build \
  --adapter benchmarks.vendor_neutral.adapters.zep_cloud:build \
  --adapter benchmarks.vendor_neutral.adapters.letta:build \
  --records 1000 --queries 100 --tenants 2 --top-k 10 \
  --output results/head-to-head.json
```

Run each system with the same host, corpus size, tenant count, query count and
top-k. Each adapter owns its system's configured embedding/retrieval pipeline.
InfinityDB's reference adapter uses the supplied deterministic feature-hash
vectors. This means the comparison measures out-of-the-box end-to-end behavior,
not a controlled embedding-model bake-off. Record provider/model configuration
and cost separately before drawing conclusions.

## What is measured

- Ingest elapsed time, throughput, p50 and p95 per-record latency.
- Query elapsed time, throughput, p50 and p95 latency.
- Exact-ID recall@k on a deterministic known-answer workload.
- Python `tracemalloc` peak allocation (not process RSS or server memory).
- Cross-tenant ID leakage observed by the adapter boundary.
- Adapter metadata and host/Python environment.

The feature-hash workload is intentionally a systems smoke test, not a semantic
retrieval benchmark. Mem0, Zep and Letta use their own configured embedding and
retrieval systems. For a fair systems comparison, pin all model revisions,
repeat runs, include cold/warm results, measure full process RSS, disk usage,
network and cloud costs, and disclose whether services are local or remote.
Zep may process graph episodes asynchronously; allow its indexing task to
complete before interpreting recall results.

## Important limitations

- The harness does not silently mock any competitor. Missing credentials,
  SDKs, agents or service availability produce explicit errors.
- Letta's agent model, memory blocks, embedding configuration and deployment
  must be disclosed; its archival search is one subsystem of a stateful agent.
- Mem0 uses local Qdrant and Hugging Face embeddings in this adapter; changing
  those settings changes the result.
- Zep is a managed cloud service here, so network latency and hosted resources
  are part of its end-to-end measurements.
- A result from this synthetic test must not be advertised as an overall
  product ranking. Add LongMemEval, LoCoMo, temporal/conflict reasoning,
  multi-hop recall, deletion, crash recovery and adversarial tenant-isolation
  suites before making memory-quality or security claims.
